## Architecture

**Stack:** React 19 + TypeScript 5.6 + Vite 7 + Tailwind CSS 4 + shadcn/ui (Radix) on the frontend. Firebase (Auth + Firestore + Cloud Functions) is the actual backend. `server/index.ts` is only an Express static file server for the built SPA — it contains no API logic. Routing is client-side via `wouter`, but navigation is **not URL-based**: `App.tsx` / `AppContext` track `currentSection` as React state, not routes, so there's no deep-linking or browser back button support for sections.

**Two Cloud Functions codebases exist — both are deployed as of 2026-08-01, as separate `firebase.json` codebases:**
- `functions/` (codebase `default`) — `dailyBackupToGoogleDrive` (scheduled, 23h Africa/Dakar) and `manualBackup` (callable), plus `getBackupDownloadUrl` (callable, regenerates a download link for an existing backup file).
- `cloud-functions/` (codebase `roles-validation`) — the server-side validation/RBAC logic: custom claims assignment, `assertRole`/`assertAdmin`/`assertAuthenticated` helpers, server-side validation of ventes/dépenses/production/clôtures, immutable audit log (`validateVente`, `validatePaiement`, `cloturerCaisse`, `annulerCloture`, `setUserClaims`, `createUserWithRole`, `toggleUserStatus`, `onUserCreate`, `onClotureWrite`, `integrityCheck`, `healthCheck`, `reauthenticate`).
- **History note:** this codebase was deployed at some earlier point outside of what `firebase.json`/git tracked (the comment header in `cloud-functions/src/index.ts` and this file both used to say "not deployed" — that was stale; the functions were live in production with real invocation counts, e.g. `validateVente` and `onClotureWrite`). `firebase.json` was updated to formally declare both codebases so future `firebase deploy --only functions` runs don't detect the `roles-validation` functions as orphaned and offer to delete them (this happened once — see git history around 2026-08-01 for the recovery). **Always check `firebase.json` and the live Firebase Console function list before assuming a codebase's deployment status from a code comment alone.**
- The client (`cfValidateVente`, `checkCloudFunctionsAvailability` in `client/src/lib/cloudFunctions.ts`) still falls back to local/client-side validation when these functions are unreachable, so the app keeps working even if this codebase were ever removed again.

**Bug: `onUserCreate` could silently strip a newly-created user's role (fixed 2026-08-03, not yet redeployed as of this writing — see below).** `createUserWithRole` (admin-only callable) creates the Firebase Auth account via `admin.auth().createUser()` and then, in the same function execution, calls `setCustomUserClaims(uid, { role, roles })` with the role the admin actually chose. But `admin.auth().createUser()` also fires the independent `onUserCreate` Auth trigger (`functions.auth.user().onCreate`) — a separate async Cloud Function invocation with no ordering guarantee relative to the rest of `createUserWithRole`. `onUserCreate` used to *unconditionally* set `role: "lecteur"` (read-only) for any email not in the hardcoded `ADMIN_EMAILS` list, so it frequently fired *after* `createUserWithRole`'s own claim-set and silently clobbered it back to `"lecteur"`. Because `firestore.rules` `canWrite()` checks `request.auth.token.role` (the Auth custom claim) and not the `users/{uid}.role` Firestore field, the app kept displaying the correct role everywhere (Utilisateurs list, sidebar, etc.) while every write from that account was actually being rejected by Firestore — and per `saveToFirestore()` in `client/src/contexts/AppContext.tsx`, sync failures are deliberately silent (no popup, only the sidebar "Erreur sync" badge — see comment there), so the only symptom a real user would notice is "everything I save disappears when I refresh." Fix: `onUserCreate` now calls `admin.auth().getUser(user.uid)` first and returns immediately if a `role` custom claim already exists, instead of always overwriting. **This fix lives in `cloud-functions/src/index.ts` but had not yet been deployed as of 2026-08-03** — run `cd cloud-functions && npm run deploy` (or `firebase deploy --only functions`) to make it effective for newly-created accounts. It does not fix already-affected accounts retroactively: for those, an admin must open Utilisateurs, re-select the user's role, and click save — this calls the (already-deployed) `setUserClaims` callable directly and re-applies the correct claim immediately, without needing a redeploy. The affected user must then log out and back in (or wait for their ID token to naturally refresh) for the corrected claim to take effect client-side.

**Backups go to Cloud Storage, not Google Drive** (changed 2026-08-01): `GUIDE_SAUVEGARDE_GOOGLE_DRIVE.md` describes the original Drive-based design, which is **no longer accurate** — a Cloud Functions service account has no personal Drive storage quota, and creating files in a Drive folder shared with it fails (`Service Accounts do not have storage quota`) unless using a paid Workspace Shared Drive or OAuth domain delegation, neither available here. `uploadToCloudStorage` in `functions/src/index.ts` now writes the Excel export to the project's default Cloud Storage bucket under `backups/<fileName>`, using a Firebase Storage download token (`firebaseStorageDownloadTokens` file metadata) rather than a GCS signed URL — signed URLs need the `iam.serviceAccounts.signBlob` permission on the Functions runtime service account, which isn't granted by default and was another dead end. `backup_logs` Firestore docs now include a `downloadUrl` field with this tokened link. `BackupsSection.tsx` has a "Sauvegarde cloud maintenant" button (admin-only) that calls `manualBackup` directly from the app UI.

**Bug: the Cloud Storage backup (`dailyBackupToGoogleDrive`/`manualBackup`) was silently backing up almost nothing for months (fixed 2026-08-18, **déployé et confirmé fonctionnel depuis le 2026-08-19** — voir `claude/investigation-doublons-ventes-2026-09-04.md` dans le projet Claude : compteurs réels et croissants dans `backup_logs.stats` depuis cette date).** `readAllData()` in `functions/src/index.ts` read `ventes`/`production`/`depenses`/`clients`/`recouvrements`/`versements` via `db.collection(col).doc("data")` — the legacy single-document format ("one doc holding an `items[]` array") that the app moved away from months ago (see "Data model" above and the "silent per-collection data loss" bug below it): `migrateArrayCollectionsToPerDocument` in `client/src/contexts/AppContext.tsx` explicitly `deleteDoc`s that `data` document once migrated, so `docSnap.exists` had been false for all of these ever since, and `livraisons`/`emballages` were read from `metaData.livraisons`/`.emballages` (the `meta/data` document) even though those two are *also* per-document `ENTITY_COLLECTIONS`, not `META_FIELDS` — so they were never populated there either, migrated or not. Net effect: the daily/manual backup ran successfully every time (`backup_logs` shows `status: "success"`), uploaded a real `.xlsx` file, and the sidebar showed "Sauvegarde cloud à jour" — while the Excel file itself had zero rows for Ventes/Production/Dépenses/Clients/Recouvrements/Versements/Livraisons/Emballages (only Commerciaux/Livreurs/Véhicules/Paramètres, which do live in `meta/data`, came through correctly). Discovered 2026-08-18 while trying to use a backup from 2026-08-17 23h to recover clients/livraisons wiped by the sync bug above — the backup turned out to have never had that data to begin with, for any date since the Phase 2 migration. Fix: `readAllData()` now reads the per-document collections with `db.collection(col).get()` (all documents) for `ventes`, `production`, `depenses`, `clients`, `recouvrements`, `versements`, `livraisons`, `emballages` — same collection names as `ENTITY_COLLECTIONS` in `client/src/lib/firestoreService.ts` — and only `maintenance`/`vehicules`/`vehiculeOps`/`commerciaux`/`livreurs`/`params` still come from `meta/data`, since those genuinely live there. **This fix lives in `functions/src/index.ts` but requires `cd functions && npm run deploy` (or `firebase deploy --only functions`) to take effect** — until deployed, the daily 23h backup and the manual "Sauvegarde cloud maintenant" button keep producing the same near-empty Excel files. It does not retroactively fix backups already taken (those files are permanently missing the data, as found here) — only prevents the gap going forward.

**Backup coverage extended to commandes/apports/caisse + new RAPPORT summary sheet (2026-08-18, déployé en même temps que le fix ci-dessus le 2026-08-19 — même fichier, même commande de déploiement ; le déploiement lui-même est confirmé, mais la présence effective des nouvelles feuilles COMMANDES/CAISSE/APPORTS/RAPPORT dans une sauvegarde serveur réelle n'a pas été vérifiée indépendamment — à confirmer sur le prochain backup généré par la Cloud Function, pas par le bouton "Sauvegarde Excel" côté client qui est un chemin totalement différent).** The user asked for the daily 23h backup to explicitly cover clients, ventes, commandes, dépenses, caisse, créances, recouvrements, apports de fonds, réception des rouleaux (livraisons), and a report — auditing `readAllData()`/`generateExcel()` found `apports` (a real per-document `ENTITY_COLLECTIONS` collection) and `commandes` (a `META_FIELDS` field on `meta/data`, like `commerciaux`/`livreurs`) were never read at all, and caisse (`DBParams.clotures`) had no worksheet. Fix: `AllData` gained `apports`, `commandes`, and `clotures` fields — `apports` added to the per-document `perDocumentCollections` list, `commandes` read from `metaData.commandes`, and `clotures` merged (by date, collection-doc wins on conflict) from both `DB.params.clotures` (the format `CaisseSection.tsx` actually reads today) and the separate `clotures` collection (written by `transactionCloture()` in `firestoreService.ts` but not yet read back anywhere client-side) — covers the backup regardless of which path a given clôture was written through. Three new worksheets: `COMMANDES`, `CAISSE` (one row per clôture), `APPORTS`. A new `RAPPORT` worksheet (placed first in the workbook) gives a one-page summary — solde de caisse actuel and créances totales reuse the exact same formulas as `computeSoldeCaisseActuel`/`cashAtSale`/`resteVente` in `client/src/lib/helpers.ts`, duplicated locally in `functions/src/index.ts` (same "no service layer" pattern as the Commande→Vente conversion — **if the client-side formulas change, port the change here too or the backup's solde/créances will silently drift from the app's**), everything else is a direct sum of the sheets already in the workbook. Also fixed while in this code: the `VENTES` sheet's "Payé"/"Reste" columns read `v.montantPaye`, a field that doesn't exist on the `Vente` type (the real field is `avance`) — so "Payé" was always 0 and "Reste" always the full montant, even for cash sales; now computed with the same `cashAtSale`/`resteVente` helpers as the créance total above. Verified with `tsc --noEmit` and `npm run build` (both pass) but **not yet deployed** — `cd functions && npm run deploy` picks up this change and the fix above in the same deploy.

**Data model — two persistence formats coexist:**
- Legacy: one Firestore doc (`meta/data`) holding all collections as arrays.
- Phase 2 (current direction): one Firestore document per entity, via `client/src/lib/firestoreService.ts` (`ENTITY_COLLECTIONS`, `subscribeToCollection`, `createEntity`, `executeBatch`, etc.).
- The switch between the two is a mutable global boolean `useNewArchitecture` in `client/src/contexts/AppContext.tsx` — it is not always obvious which path a given write takes. `ENTITY_FIELDS` and `META_FIELDS` in that same file list which logical collections belong to which format (there's overlap by design during the migration: `commerciaux`, `livreurs`, `maintenance`, `vehicules`, `users`, `vehiculeOps`, `commandes` currently live in `META_FIELDS`, i.e. the lightweight single-doc `params`-style storage).

**Bug: silent per-collection data loss on save before the first real Firestore snapshot (fixed 2026-08-18).** `saveToFirestore` in `AppContext.tsx` writes the per-document collections (`ventes`, `clients`, `production`, `depenses`, `recouvrements`, `livraisons`, `emballages`, `versements`, `apports`, `mouvementsStock`, `journal`, `history`, `reconciliations`, `corbeille`, `stockControles` — the `diffedCollections` map) by diffing the current local `DB[field]` array against `lastSyncedItemsRef.current[field]` (the last state actually confirmed from a Firestore `onSnapshot`), and issuing a real `deleteDoc()` for every document present in that last-known state but missing from the current local array — see the "Correctif critique" comment above `diffedCollections` for why the diff exists (avoid one user's save clobbering another's concurrent add). The gap: unlike `meta/data` (`metaLoadedRef`) and `params/global` (`paramsLoadedRef`), this diff had **no guard** verifying that the field's first real Firestore snapshot had actually been applied to local state before trusting the diff. `saveDB()` writes ALL fields on every call, regardless of which module triggered it, so if `DB.clients` or `DB.livraisons` was transiently incomplete locally in someone's browser (page reload race, slow/dropped listener) *after* a real snapshot had already set `lastSyncedItemsRef.current.clients` to the full list, the next save from that tab — triggered by any unrelated action, e.g. adding a `vente` — read that gap as "these documents were deleted by the user" and silently issued real `deleteDoc()` calls for all of them. This path never calls `logActivity` and never routes through the Corbeille (both of those only happen on an explicit user delete button), so the resulting data loss leaves **no trace in Journal/Historique/Corbeille** — this is what happened to the `clients` and `livraisons` collections around 2026-08-18 while `ventes`/`depenses`/`production` were unaffected (confirmed: sync indicator green at the time, so it wasn't a stale/disconnected client; no matching Journal entries; not the Paramètres "Purger" button, which explicitly preserves `clients`; not a Sauvegardes restore). Fix: a new `collectionsLoadedRef.current[field]` ref, set `true` only inside the `entityCollections` `onSnapshot` callback in `setupFirestoreSync` (after applying — even an empty — real snapshot for that field), and checked at the top of the `diffedCollections.forEach` loop in `saveToFirestore` — if a field hasn't received its first real snapshot yet in this session, that field is skipped entirely for this save (no set, no delete) rather than diffed against a reference that might not reflect reality yet. Same protective pattern as `metaLoadedRef`/`paramsLoadedRef`, just applied per-collection instead of to the two singleton documents.

**Follow-up fix to the bug above: the `collectionsLoadedRef` guard also silently dropped legitimate new writes, not just bad deletes (fixed 2026-08-18).** The original fix skipped the *entire* field (both the `setDoc` create/update loop and the `deleteDoc` loop) whenever `collectionsLoadedRef.current[field]` was still `false` — safe for deletes, but wrong for creates: any `setDoc` for a brand-new item queued in that same save was silently thrown away too, with no error and no retry, if it happened before that collection's first real Firestore snapshot had loaded in the current tab. Discovered when a CSV import of 203 clients (done right after a page load) left only 151 clients in Firestore, and the import's own `logActivity` (which itself writes to the `journal` field, also gated by the same guard) never made it to Firestore either — so the Journal showed *zero* trace of the import, even though it had visibly succeeded in the UI at the time. Because the loss happens before the next real snapshot arrives, a refresh before that snapshot lands loses the data from local state too, not just from Firestore. Fix: in the `diffedCollections.forEach` loop, the create/update (`setDoc`) loop now always runs unconditionally — at worst, if `prevItems` is still `[]` because no real snapshot has landed yet, it just re-`setDoc`s documents that are already identical server-side, which is a no-op. Only the `deleteDoc` loop stays behind `if (collectionsLoadedRef.current[field])`, since that's the only direction that can destroy real data. This asymmetry (create = always safe to send, delete = only once the field is confirmed loaded) is what actually needed fixing; `meta/data` and `params/global` don't have this follow-up issue since those are written as a single whole-document `setDoc`/merge, not diffed per item, so blocking the write entirely before load is correct there.

**Bug: silent data loss on the meta/data document (commandes and other META_FIELDS), fixed 2026-08-19.** Unlike the per-document `ENTITY_COLLECTIONS` above, `META_FIELDS` (`commandes`, `livreurs`, `commerciaux`, `vehicules`, `maintenance`, `vehiculeOps`, `users`, `producteurs`, `avances`, `approvals`, `auditChain`) all live as array fields on a single shared document, `meta/data`. `saveToFirestore` used to write each of these fields **in one block** straight from local state (`metaData[field] = data[field] || []`) on every single `saveDB()` call, from any module — Firestore never merges an array field element-by-element even with `{merge:true}`, it always replaces the whole value, so any staleness in one client's local copy of e.g. `commandes` silently erased a commande another user/tab had just added and synced successfully, the moment this client made ANY unrelated save. The listener made this worse: `setupFirestoreSync`'s `meta/data` `onSnapshot` used one **global** anti-echo window (`lastLocalSaveRef`, shared by every META_FIELD) instead of the per-field one already used for `ENTITY_COLLECTIONS` (`lastFieldSaveRef`) — saving `livreurs` on one tab could suppress that tab from picking up a concurrent `commandes` addition for up to 5s, during which any further local save on that tab would ship a `commandes` array still missing the new entry. Separately, the blanket "BLOQUÉ" freshness pre-check in `saveToFirestore` (comparing `meta/data.lastUpdate` against the last successful local write) could permanently strand an offline-created commande: `flushQueue()` (the reconnect handler in the `onConnectivityChange` effect) called `clearSyncQueue()` unconditionally right after `saveToFirestore`, even when that pre-check silently blocked the write and sent nothing — so a commande typed while offline, then "synced" at reconnect after someone else had touched `meta/data` in the meantime, was marked as flushed without ever reaching Firestore, and vanished on the next page load once the listener reapplied the real (commande-less) server state. This combination is almost certainly what CommandesSection.tsx users were seeing as "typed commandes disappearing." Fix, in `AppContext.tsx`: (1) a new `lastSyncedMetaItemsRef` tracks the last known Firestore array per META_FIELD, mirroring `lastSyncedItemsRef` for entity collections; (2) `saveToFirestore`'s meta write now does a 3-way merge per field instead of a blind overwrite — it re-reads `meta/data` fresh right before writing, drops only the items this client itself deleted (diffed against its own `lastSyncedMetaItemsRef` baseline), and overlays its own local adds/edits on top of that freshly-read remote state, so a concurrent addition from another client always survives; (3) the `meta/data` listener's anti-echo is now per-field (reusing `lastFieldSaveRef`) instead of one global window for the whole document; (4) the blanket freshness pre-check at the top of `saveToFirestore` was removed entirely — now redundant given (2) and the pre-existing per-item diff on `ENTITY_COLLECTIONS` make blind overwrites safe regardless of which side is "newer"; `saveToFirestore` now returns a boolean, and `flushQueue()` only calls `clearSyncQueue()` when it returned `true`, so a blocked/failed flush keeps retrying instead of being marked done. (5) `saveDB`'s 60/minute rate limit no longer drops a save silently when hit — it schedules a retry via `setTimeout` once the window resets. Verified with `tsc --noEmit` (0 errors). If `commandes` keeps growing (see the note on `META_FIELDS` above), migrating it to `ENTITY_COLLECTIONS` remains the more robust long-term fix — it would get per-document writes for free instead of relying on this client-side merge.

**State management:** a single monolithic `AppContext` (`client/src/contexts/AppContext.tsx`, ~500+ lines) holds the entire app state — every collection, all params, current user, sync status — via one `DB: Database` object. Any collection update re-renders everything subscribed to the context. There is no per-domain context split (e.g. AuthContext vs DataContext) yet.

**No service layer:** section components (`client/src/components/sections/*.tsx`, one file per business module — Ventes, Clients, Production, Caisse, Livreurs, etc.) call `setDB` + `saveDB` + `logActivity` directly and often embed business logic (e.g. commission calculations) inline in JSX rather than delegating to a dedicated service module.

**Balance vs flux — a recurring trap in KPI code.** Two different kinds of numbers show up throughout the app, and conflating them is an easy, repeatable mistake: a **balance** (solde de caisse, stock restant, créances totales) is cumulative — the state right now, computed over the *entire* history — while a **flux** (ventes du mois, dépenses de la semaine, production du jour) is scoped to whatever period filter (`aujourd'hui`/`semaine`/`mois`/`mois-precedent`/`personnalise`) the user has selected and is meant to reset to zero for a new period. `DB.params.soldeOuverture` (opening cash balance) is the sharpest example: it's a one-time constant that only belongs in a balance calculation, added exactly once over the full history — never inside a period-filtered sum, or it gets re-added in full every time a period is viewed (this exact bug shipped in both `CaisseSection.tsx` and `Dashboard.tsx` independently and was fixed 2026-08-03; see git history around that date). To stop this from recurring a third time, the balance calculations now live in one place — `computeSoldeCaisseActuel(DB)` and `computeStockRestant(DB)` in `client/src/lib/helpers.ts` — used by `CaisseSection.tsx`, `Dashboard.tsx`, `client/src/lib/tests-calculs.ts`, and `ExportExcel.tsx` instead of each reimplementing its own variant. Any new balance-type KPI should call these (or a new function added next to them), not recompute inline. `computeStockRestant(DB)` itself was fixed 2026-08-03 to stop being its own independent balance path: it used to recompute "total production − total ventes − total bonus" straight from `DB.production`/`DB.ventes`, a completely separate calculation from the `DB.mouvementsStock` journal that `StockSection.tsx`/`calculerStockParEmplacement` (`client/src/lib/stock.ts`) replays — so the Dashboard's "Stock restant (total)" card and Gestion du Stock's "Stock total packs" card could (and did) disagree, since the Dashboard's version ignored casses/pertes, manual ajustements, and any "Nouveau départ" reset (see below). `computeStockRestant` now delegates to `calculerStockParEmplacement(DB.mouvementsStock)` filtered to `sachet_plein` summed across every emplacement, so both screens are now guaranteed to show the same number by construction — don't reintroduce a second independent stock formula. In the UI, balance cards are shown independent of the period selector (e.g. "Solde de caisse actuel" in `CaisseSection.tsx`/`Dashboard.tsx` sits outside the period-filtered KPI row), and labels should say "(total)"/"(actuel)" for balances vs "(ce mois)"/"(période)" for flux so the distinction is visible without reading code.

**Bug stock camions (fixed 2026-08-03).** `client/src/lib/stock.ts` models per-location stock (`usine`, `depot`, `camion_<id>`) by replaying a journal of `MouvementStock` entries (`DB.mouvementsStock`), each with an `emplacementSource`/`emplacementDest`. Two independent code paths write to `camion_<id>` keys and, until this fix, used two different ID namespaces: the "Chargement" flow in `StockSection.tsx` credits `camion_<vehiculeId>` (a real `Vehicule.id`), while `VentesSection.tsx` — when a vente has a `livreur` assigned — used to debit `camion_<livreurObj.id>` (a `Livreur.id`, an entirely separate ID space, since `Livreur` and `Vehicule` are unrelated entities with independently-generated `uid()`s and no stored link between them). The two keys essentially never matched, so every delivered vente drained a phantom `camion_<livreurId>` location that no chargement ever fed, driving all camion balances steadily negative while the usine balance was never correctly decremented for those sales (it looked artificially high) — this is exactly the "Stock négatif" state a user reported seeing across every camion card in `StockSection.tsx`, "Stock actuel" tab. Fix: `Livreur` (`client/src/lib/types.ts`) gained an optional `vehiculeId` field — the camion a livreur currently drives, settable in `LivreursSection.tsx` — and `VentesSection.tsx` now resolves the vente's stock source as `camion_${livreurObj.vehiculeId}` when set, falling back to `"usine"` (not a fake livreur-keyed location) when a livreur has no camion assigned. Because this bug had already written bad `emplacementSource`/`emplacementDest` values into production Firestore data, `StockSection.tsx` also gained an admin-only repair tool (`repairPlan`/`handleRepair`, surfaced via a red alert banner + "Réparer les mouvements de stock mal orientés" dialog when `Livreur.id`-keyed camion movements are detected) that reassigns those historical movements to the livreur's now-assigned camion, or to usine if still unassigned. Admins should assign each livreur's camion in Livreurs *before* running the repair tool for the most accurate reattribution. This only fixes the `sachet_plein` (packs) side of the ledger; a separately-observed negative `rouleau_plastique` (kg) balance at usine was unrelated (see below — that product is no longer tracked in Gestion du Stock at all).

**Stock: "Nouveau départ" reset + rouleau_plastique (kg plastique) removed from tracking (2026-08-03).** Two follow-up changes on top of the camion bug fix above, both in `StockSection.tsx`:

Trucks without a `capacitePacks` on their `Livreur` record default to `CAPACITE_CAMION_DEFAUT` (110 packs, a `CommandesSection.tsx` constant) rather than "no limit" — reflects the real fleet's truck capacity, still overridable per truck/run in the dialog. **Dispatching — affinage par itinéraire routier réel (added 2026-08-15).** `client/src/lib/routing.ts` (new file) optionally refines the sweep/nearest-neighbor result above with a real Google Directions call per truck (`raffinerTourneeAvecItineraireReel`/`raffinerDispatchingAvecItineraireReel`): `origin`/`destination` = depot, `waypoints` = the truck's stops, `optimizeWaypoints: true` (an approximate TSP solve, better stop ordering than the offline nearest-neighbor), `travelMode: "DRIVING"`. **Security hardening: business-rule validation and clôture lock moved into `firestore.rules` itself (2026-08-29, not yet deployed as of this writing).** User-reported concern: `firestore.rules` only ever checked the caller's *role* (`canWrite()`), never the *shape* of the data being written nor whether the target date belonged to an already-clôturée day — so a caissier/commercial bypassing the normal screens (raw Firestore SDK calls, browser devtools, direct REST) could create a 0-F/negative-packs vente, write an arbitrary stock movement, or edit a vente/dépense/mouvement from a day already closed, none of which the server would reject. The real business validation (`validateVente`, `validatePaiement`, `cloturerCaisse` in `cloud-functions/src/index.ts`) only runs when the client goes through those callables — and per "no client-side fallback" above, the app deliberately falls back to writing Firestore directly when Cloud Functions are unreachable, so this gap was reachable even without malicious intent, just a network blip. Fix, entirely in `firestore.rules`: new `valid*()` functions (`venteValide`, `depenseValide`, `productionValide`, `recouvrementValide`, `versementValide`, `apportValide`, `mouvementStockValide`) re-check the same bounds as the Cloud Functions (positive/max packs & prix, known `mode`/`type`/`produit`/`unite` enums, avance ≤ montant total, non-empty required fields) directly in the rules, applied to `create`/`update` on `ventes`, `depenses`, `production`, `recouvrements`, `versements`, `apports`, `mouvements_stock`; and a new `dateEstVerrouillee(date)` function blocks **any** create/update/delete (including by an admin) on those same seven collections once the document's date — before or after the write — is in `params/global.clotureesDates`, a new flat `string[]` field. `clotureesDates` is recomputed in full from `params/global.clotures[]` every time `cloturerCaisse`/`annulerCloture` (Cloud Functions) or `createCloture`/`annulerCloture` (`client/src/lib/cloture.ts`, the local fallback path) run — the existing `clotures[]` array of heterogeneous objects can't be tested for "does any entry have this date" directly in Firestore's rules language (no `.filter()`/predicate support on lists), hence the separate flat field. Once a day is locked this way, the *only* path back in is `annulerCloture` (admin, ≥10-char motif, audited) — a direct Firestore write, even from an admin session, is refused. Added `DBParams.clotureesDates?: string[]` (`types.ts`) and — same trap as `primesPaliers`/`budgetsDepenses` documented elsewhere in this file — added it to `normalizeParams()`'s optional-key allowlist in `AppContext.tsx`, or the next unrelated Paramètres save by an admin would silently strip it from `params/global` and re-open every previously-closed day. New admin-only callable `backfillClotureesDates` (`cloud-functions/src/index.ts`) recomputes `clotureesDates` from the full `clotures[]` history in one shot — **must be called once after this deploys**, since days closed before this change won't be in `clotureesDates` (and therefore stay unlocked at the rules level) until either this callable runs or that specific day is touched by `cloturerCaisse`/`annulerCloture` again. Recouvrements (paiements) still can't have their "montant ≤ reste à payer" check fully replicated in rules (would need summing every existing recouvrement for the vente, not practical in the rules language) — that check remains Cloud-Function-only; the rules-level fix only closes the negative/zero-amount and clôture-bypass angles for that collection. Deliberately **not extended** to `maintenance`/`vehiculeOps`/`commandes`: those three live inside `meta/data` as whole-array `META_FIELDS` (see "Data model" above), not as individual documents, so a per-item date/shape check isn't practical in rules without first migrating them to `ENTITY_COLLECTIONS` — flagged as a follow-up, same migration already recommended for `commandes` elsewhere in this file. **Deployment: `firebase deploy --only firestore:rules,functions:roles-validation` (or the full `cd cloud-functions && npm run deploy` for the functions half) has NOT been run from this environment** — this sandbox has no `firebase` CLI/credentials — then call `backfillClotureesDates` once (e.g. via the Firebase Console's function-testing UI, or a temporary authenticated call from the app) to cover already-closed days. `tsc --noEmit` clean on both `client/` and `cloud-functions/` after this change.

**Known architectural issues to keep in mind before extending code** (from `AUDIT-COMPLET-MA2F-AQUASACHET.md`, full detail there):
- Field name mismatch between `firestore.rules` (`quantite`/`prixUnitaire`) and the app/Cloud Functions (`packs`/`prix`) for `ventes` — check current rules before assuming client writes will pass.
- Double-write risk on vente creation: when Cloud Functions are reachable, a vente can be created both server-side (CF) and client-side, producing duplicates.
- Commission and bonus are computed live from current params (`taux`, `bonusSeuil`) rather than snapshotted at transaction time, so historical figures can shift retroactively if params change.
- No server-side pagination — all Firestore listeners (`onSnapshot`) pull entire collections; fine under ~5000 ventes, degrades past that.

**Suivi GPS temps réel des camions — boîtier physique (added 2026-08-22).** A different data source from the phone-geolocation gap noted above: this tracks a dedicated GPS device installed IN the truck (e.g. a Concox GT06-class tracker wired to the battery or plugged into OBD-II), reporting through its own cellular SIM to a tracking platform (vendor platform, or a self-hosted one like Traccar), independent of the livreur's phone being on/open. MA2F's side of this is built and ready to receive positions from whichever platform the business ends up choosing — nothing here talks to a specific tracker's native protocol.
- `Vehicule.traceurId` (`types.ts`, editable in `VehiculesSection.tsx`'s camion dialog) holds the physical tracker's identifier (IMEI, or the tracking platform's "device id") — the join key between a real-world box and a `Vehicule` record. Duplicate-checked like `Vehicule.nom` already was (two trucks can't share one tracker). Empty = no box installed yet, no positions will ever arrive for that truck.
- `cloud-functions/src/index.ts`'s `recevoirPositionVehicule` (HTTP `onRequest`, **not** an `onCall` — an external tracker/relay can't authenticate with the Firebase client SDK) is a generic webhook: POST a JSON body `{ traceurId, lat, lng, vitesseKmH?, capDegres?, horodatage? }` with header `X-Webhook-Secret` matching the `GPS_WEBHOOK_SECRET` env var (see `cloud-functions/.env.example`; generate with `openssl rand -hex 32`), and it resolves `traceurId` → `Vehicule` (reading `meta/data.vehicules`, same lightweight-doc format as everywhere else `vehicules` lives — see "Data model" above) and upserts `positionsVehicules/{vehiculeId}`. Rejects with 404 if `traceurId` doesn't match any `Vehicule.traceurId` (associate it in Véhicules first), 400 on a coordinate outside a generous Senegal bounding box (catches the classic "0,0 before first GPS fix" glitch), 401 on a wrong/missing secret. **Nothing calls this webhook yet** — it's the receiving end, built ahead of picking hardware/platform on purpose (so the platform choice doesn't block having somewhere to send positions to). Whatever gets chosen (a vendor's own webhook feature, or a small relay script polling e.g. Traccar's REST API — https://www.traccar.org/api-reference/ — and re-POSTing here) just needs to speak this JSON shape. Must be deployed (`cd cloud-functions && npm run deploy`, after setting `GPS_WEBHOOK_SECRET` — writing a Cloud Function in this repo isn't the same as it being live, see several "fixed but not yet deployed" entries elsewhere in this file for why that distinction matters here) before any real device can use it, and its URL (`https://<region>-<project>.cloudfunctions.net/recevoirPositionVehicule` once deployed) is what gets configured on the tracker/platform/relay side.
- `positionsVehicules/{vehiculeId}` (new `PositionVehicule` type in `types.ts`) holds only the LATEST known position per truck (overwritten on each update, not a trip history/trail — a history subcollection would be a separate addition if route-replay is ever wanted) plus a server-set `_receivedAt` timestamp. `firestore.rules` locks it down the same way as `mobileMoneyIntents`: `allow read: if isAuthenticated()`, `allow write: if false` — only the Cloud Function's Admin SDK (which bypasses rules) can ever write here, so a compromised/rooted client account can't spoof a truck's location.
- `SuiviLogistiqueSection.tsx` subscribes directly to `positionsVehicules` via `onSnapshot` (bypassing `AppContext`/`DB`, same pattern as `RecouvrementSection.tsx`'s `mobileMoneyIntents` listener — this data doesn't belong in the big `DB` object) and renders each truck as a distinct 🚛 marker (bigger than the small commande dots, `zIndex: 999` so it sits above them), colored to match whichever livreur currently drives it (`Livreur.vehiculeId`, same palette as commande markers). Gated to `carteDate === todayLocal()` only — a live position next to a past/future day's commandes would be misleading, so the truck layer is simply empty on any other date. A truck whose last position is older than `POSITION_PERIMEE_APRES_MIN` (30 min) renders grayed-out rather than disappearing — a stale signal (dead battery, unplugged box, connectivity gap) is itself useful information, not something to silently hide. The "Carte des tournées" card now also renders when there are live trucks but zero commandes for the day (previously gated on `commandesJour.length > 0` alone, which would have hidden a truck-only view).
- **Not yet built, deliberately out of scope here**: nothing picks a tracker brand, SIM/data plan, or hosts a Traccar (or equivalent) instance — those are hardware/vendor/ops decisions for the business to make, this only prepared the MA2F-side plumbing so building it isn't blocked on that choice. If asked to go further, the next real step is either (a) standing up Traccar (or accepting a vendor's own webhook) and wiring its output to POST to `recevoirPositionVehicule`, or (b) if a vendor platform has no webhook, a small always-on relay (a tiny script/service, NOT a Cloud Function on a schedule shorter than 1 min) polling that platform's API and re-POSTing each position here.

**Fix: whole database was being cached in plaintext `localStorage` (fixed 2026-08-29, found via a client-reported security audit finding).** Despite the AES-GCM encrypted store above, `AppContext.tsx` also wrote the **entire** `Database` object — ventes, clients, caisse, dépenses, users, everything — as plain JSON to `localStorage["ma2f_db_sync"]` on every `saveDB()` and on every Firestore listener update, plus read it back synchronously on mount before the encrypted store resolved. This existed as a "survive a refresh before the async encrypt finishes" / "instant first paint" fallback, but it meant the whole business database sat in cleartext in the browser indefinitely — readable by any browser extension with storage access, anyone with access to the machine, or (on a shared/former-employee device) long after the session ended, since nothing ever cleared it, including at logout. Fix: removed all `ma2f_db_sync` reads/writes — `AppContext.tsx` now relies solely on the AES-GCM encrypted IndexedDB-backed store (`encryptAndStore`/`decryptFromStorage`) for local persistence; the brief moment before that resolves on mount is already covered by the "Connexion à Firebase..." loading screen in `App.tsx`. `logout()` (`AppContext.tsx`) now calls the (now-async) `clearSecureStorage()` — which removes the encrypted blob, deletes the AES-GCM key itself from its `ma2f_keys` IndexedDB store (forcing a fresh key next login, so no stale key persists across users of a shared device), and cleans up any legacy plaintext residue (`qprost_db`, `ma2f_db_sync`) plus session metadata (`ma2f_last_update`, `ma2f_last_sync`, `ma2f_sync_queue`, `ma2f_failed_ops`) — and `clearSyncQueue()` (`offlineSync.ts`, which now also clears `ma2f_failed_ops`, not just the pending queue), then resets in-memory `DB` state to `DEFAULT_DB`. Net effect: nothing business-sensitive remains in the browser once a user logs out. `tsc --noEmit`: 0 errors. **Not yet addressed, worth a follow-up:** `client/src/lib/offlineSync.ts`'s `PendingOperation.data` field is a generic `Record<string, any>` that could carry real entity payloads into `localStorage["ma2f_sync_queue"]"`/`"ma2f_failed_ops"` in plaintext if a future caller of `enqueueOperation` passes real data (today's only call site in `AppContext.tsx` only passes `{ timestamp }`, so this is currently latent, not exploited).

**Sécurisation de meta/data (« centre de contrôle ») — séparation admin/opérationnel (added 2026-08-29).** Audit signalé par l'utilisateur : `meta/data` (voir "Data model" ci-dessus) regroupe dans UN SEUL document Firestore des champs opérationnels (commerciaux, livreurs, commandes, véhicules, maintenance, vehiculeOps, producteurs, avances, employes) ET des champs sensibles (`users`, `params`, `approvals`, `auditChain`) — et `firestore.rules` n'accordait jusqu'ici qu'une seule permission `allow write: if canWrite()` pour tout le document, donc n'importe quel caissier/commercial pouvait, via un appel direct au SDK Firestore ou aux DevTools (pas via l'écran normal, qui le bloque déjà côté UI), réécrire les comptes utilisateurs, les paramètres globaux, le statut d'une demande d'approbation ou la chaîne d'audit — exactement le scénario que `canApprove()` (`approvalWorkflow.ts`) ne bloquait que côté client. Fix, en deux parties :

1. `firestore.rules` `match /meta/{docId}` : `users`/`params` sont désormais entièrement réservés à `isAdmin()` (`diff().affectedKeys().hasAny(['users','params'])` interdit pour un rôle opérationnel). `approvals`/`auditChain` restent modifiables par tout rôle `canWrite()` mais uniquement en AJOUT — `metaApprovalsAppendOnly()`/`metaAuditChainAppendOnly()` utilisent `list.hasAll()` pour garantir que l'intégralité du contenu déjà présent reste un sous-ensemble du nouveau contenu, peu importe l'ordre, donc un caissier/commercial peut créer une demande d'approbation ou générer une entrée d'audit (usage quotidien légitime — voir `ApprobationsSection.tsx`/`logActivity`) mais ne peut ni approuver/rejeter une demande existante ni altérer/purger la chaîne d'audit. Même durcissement appliqué à `journal/{docId}` et `history/{docId}` (jusqu'ici `allow write: if canWrite()` aussi, donc update/delete ouverts à tous) : `logActivity()`/`createHistoryEntry()`/`updateHistoryEntry()`/`deleteHistoryEntry()` ne créent jamais qu'une NOUVELLE entrée décrivant une action (vérifié dans `history.ts` — aucun code ne modifie/supprime jamais un document déjà écrit, seule la purge admin de `ParametresSection.tsx` vide ces tableaux), donc `allow create: if canWrite(); allow update, delete: if isAdmin();` ne casse aucun flux existant. `users/{userId}` et `params/global` étaient déjà admin-only (inchangés).
2. `client/src/contexts/AppContext.tsx` `saveToFirestore` : côté client, `META_FIELDS.forEach` exclut désormais entièrement `users`/`params` de l'écriture `meta/data` d'un rôle non-admin (`isAdminUser`, calculé une fois en haut de la fonction et réutilisé pour la garde `params/global` déjà existante) — nécessaire car sinon la règle ci-dessus aurait rejeté en bloc TOUTE la sauvegarde meta/data (commandes, livreurs, etc. compris) dès que le miroir local de `users`/`params` d'un caissier/commercial différait, même légèrement, de l'état distant. Le `setDoc(metaDocRef, ...)` est passé en `{ merge: true }` (il ne l'était pas avant) : indispensable pour que les champs désormais omis par un rôle opérationnel restent intacts dans Firestore au lieu d'être effacés par un remplacement intégral du document. `tsc --noEmit` : 0 erreur.

**Ces règles ont été modifiées dans `firestore.rules` mais nécessitent `firebase deploy --only firestore:rules` pour être effectives** — tant que ce déploiement n'est pas fait, l'ancienne règle (`allow write: if canWrite()`) reste active en production sur `meta/{docId}`/`journal/{docId}`/`history/{docId}`.

**Fix: sauvegardes JSON restaurables silencieusement bloquées depuis le 2026-08-06 par la limite de 1 Mo/document Firestore (fixed 2026-09-04, storage.rules déployé le 2026-09-04 — `firebase deploy --only storage`, confirmé réussi).** Distinct du pipeline Excel→Cloud Storage documenté plus haut ("Backups go to Cloud Storage") : `BackupsSection.tsx` maintient un second système de sauvegarde, un JSON complet de toute la base (`DB.backups[]`, `snapshotSansBackups(DB)`), créé automatiquement une fois par jour (si un admin a l'onglet Sauvegardes ouvert) ou manuellement via "Sauvegarde manuelle" — c'est le seul des deux formats réellement restaurable (le bouton "Restaurer" ne s'applique qu'à celui-ci). Avant ce correctif, chaque sauvegarde était écrite intégralement (champ `data` = `JSON.stringify` de toute la base) directement dans le document Firestore `backups/<id>`, avec un garde-fou interne (`FIRESTORE_BACKUP_SIZE_LIMIT = 900_000` octets) qui abandonnait silencieusement la réplication cloud au-delà — mais seul le bouton manuel affichait un avertissement dans ce cas, jamais la sauvegarde automatique horaire (`setInterval`), qui échouait sans qu'aucun admin ne le remarque. Investigation (voir `claude/fix-backups-storage-2026-09-04.md` dans le projet Claude) : la dernière sauvegarde restaurable réussie dans la console Firebase datait du 2026-08-06 (888 189 octets, juste sous le seuil) — la base ayant grossi depuis (ventes, production, mouvements de stock), l'export JSON complet dépasse maintenant systématiquement la limite réelle de Firestore (~1 MiB/document), donc plus aucune sauvegarde restaurable n'était produite depuis près d'un mois, sans aucun signal visible. Fix, suivant exactement le pattern déjà établi pour les sauvegardes Excel (`uploadToCloudStorage` dans `functions/src/index.ts`, voir plus haut) : le JSON complet est maintenant uploadé côté client vers Firebase Storage, sous `backups_json/<id>.json` (`uploadBackupToStorage`/`deleteBackupFromStorage`, nouvelles fonctions dans `BackupsSection.tsx`), et le document Firestore `backups/<id>` ne garde plus qu'un pointeur léger : `{id, date, type, taille, storagePath}` — quelques centaines d'octets, très loin de la limite, donc plus jamais de risque de dépassement au fil de la croissance de la base. `Backup.data` (`types.ts`) devient optionnel et `Backup.storagePath?: string` est ajouté ; une nouvelle fonction `getBackupData(backup)` gère les deux formats : `data` inline s'il est présent (format historique, ou une sauvegarde encore en mémoire locale dans l'onglet qui vient de la créer — voir note ci-dessous), sinon téléchargement depuis Storage via `getBytes()` du SDK (pas un `fetch()` brut sur une URL — évite tout souci de CORS et respecte nativement les règles Storage avec le token d'auth de l'utilisateur). `handleDownload`/`handleRestore`/`handleTestRestore` passent tous par cette fonction et sont donc devenus asynchrones ; la suppression (`confirmDelete`) et la rotation (30 sauvegardes max, `checkAutoBackup`/`handleBackup`) suppriment maintenant aussi l'objet Storage correspondant en plus du document Firestore, pour ne pas laisser de fichiers orphelins s'accumuler dans le bucket. **Nuance importante sur le format `data`/`storagePath` :** ce n'est pas strictement "ancien vs nouveau format" par date — c'est que le listener Firestore `onSnapshot` sur `backups` (`AppContext.tsx`, réservé aux admins) hydrate `DB.backups` depuis les documents Firestore, qui pour toute sauvegarde créée après ce correctif ne contiennent QUE `storagePath` (jamais `data`, volontairement, pour rester légers) ; seul l'onglet qui a créé la sauvegarde garde `data` inline en mémoire locale jusqu'au prochain rechargement de page. Les sauvegardes créées avant ce correctif gardent `data` inline dans Firestore indéfiniment (compatibilité descendante assurée par `getBackupData`, jamais migrées automatiquement en masse — seule l'ancienne routine de nettoyage des sauvegardes "auto-incluses" bloatées, si elle se déclenche sur une sauvegarde donnée, la réécrit au passage au nouveau format via le `syncBackupToFirestore` déjà modifié). Nouveau fichier `storage.rules` à la racine du dépôt (aucun n'existait avant dans ce dépôt) : accès à `backups_json/*` réservé au custom claim `role == 'admin'` (même pattern que `isAdmin()` dans `firestore.rules`), deny-all explicite pour tout le reste du bucket — n'interfère pas avec le préfixe `backups/<fileName>` déjà utilisé par les Cloud Functions Excel (celles-ci écrivent via le SDK Admin, qui ignore les règles Storage, et se lisent via un `downloadUrl` à token, pas via le SDK client). `firebase.json` gagne la clé `"storage": { "rules": "storage.rules" }` pour que ce fichier soit pris en compte au déploiement. **Déployé le 2026-09-04 par l'utilisateur depuis son propre terminal** (`firebase deploy --only storage`, "Deploy complete!" confirmé). Piège rencontré au premier essai : `firebase deploy --only storage:rules` échoue avec "Could not find rules for the following storage targets: rules" — contrairement à Firestore (`firestore:rules`/`firestore:indexes`), Storage n'a pas de sous-cible nommée "rules" (le suffixe après `:` y est traité comme un nom de cible multi-bucket, inexistante ici) ; la commande correcte est `firebase deploy --only storage` tout court, qui déploie les règles (seul artefact Storage déployable). **Reste à vérifier en conditions réelles dans l'app** (créer une sauvegarde manuelle depuis Sauvegardes, confirmer que le document Firestore `backups/<id>` reste léger sans champ `data`, et que Restaurer/Télécharger/Tester l'intégrité fonctionnent sur cette nouvelle sauvegarde) — pas encore fait au moment de cette note. `npx tsc --noEmit` : 0 erreur. `npx vite build` non vérifié dans cette session (indisponible en pratique dans le temps imparti pour lancer un build complet depuis la machine locale via le pont de fichiers).

**Bug: collisions de N° BL — deux ventes différentes recevant le même numéro (fixed 2026-09-04).** Repéré en comparant une sauvegarde Excel du 20/08 à un export du 04/09 (`claude/fix-backups-storage-2026-09-04.md` dans le projet Claude — comparatif fait à la demande de l'utilisateur) : 9 numéros de BL (ex: BL-777, BL-141...) portés chacun par 2 à 3 ventes bien réelles et distinctes (clients, montants, parfois dates différents) — à ne pas confondre avec les ~751 doublons Firestore nettoyés le même jour (voir `claude/investigation-doublons-ventes-2026-09-04.md`), qui étaient de vrais doublons du même enregistrement avec des IDs Firestore auto-générés, pas des collisions de numéro métier. Cause : `VentesSection.tsx` calculait le numéro suggéré à l'ouverture du formulaire "Nouvelle vente" par `"BL-" + (DB.ventes.length + 1)` — purement local à l'état React de l'onglet/appareil qui ouvre le formulaire, jamais un compteur serveur. Quand deux commerciaux ouvraient ce formulaire à peu près au même moment sur deux appareils différents, chacun voyait sa propre copie de `DB.ventes` (pas forcément encore synchronisée avec la vente que l'autre venait tout juste de créer) et calculait donc le même numéro suivant ; le champ reste modifiable mais personne ne le change en pratique. Fix : nouvelle fonction `allouerProchainNumeroVente(currentMax)` dans `VentesSection.tsx`, qui alloue le numéro via une transaction Firestore atomique sur un nouveau document compteur partagé, `meta/compteurs` (champ `ventesNumero`) — deux appels concurrents ne peuvent jamais recevoir la même valeur, même déclenchés à la même milliseconde depuis deux appareils. `currentMax` (le plus grand suffixe numérique déjà vu dans `DB.ventes` au moment de l'appel, via la nouvelle fonction `numeroVenteValeur()`) sert d'amorçage/rattrapage : la transaction repart toujours d'au moins `max(compteur stocké, currentMax) + 1`, donc même un numéro saisi/importé à la main au-delà de la valeur du compteur (ou le tout premier appel, avant que le compteur n'existe) ne peut jamais faire réattribuer un numéro déjà utilisé. `handleOpen` (ouverture du formulaire) affiche toujours immédiatement un numéro provisoire (même ancien calcul, pour ne pas laisser le champ vide pendant l'aller-retour réseau) puis le remplace par le numéro réel une fois la transaction résolue — sauf si l'utilisateur a déjà modifié le champ entre-temps (comparaison à la valeur provisoire via un `setNumero` fonctionnel). En cas d'échec (ex: hors-ligne), le numéro provisoire reste affiché en secours — le risque de collision réapparaît dans ce cas rare, mais mieux que de bloquer la saisie. **Aucun changement `firestore.rules` nécessaire** : `match /meta/{docId}` est déjà générique (n'importe quel `docId` sous `meta`, pas seulement `meta/data`) et `canWrite()` (admin/caissier/commercial) couvre déjà l'écriture d'un champ qui n'est ni `users` ni `params` ni `approvals`/`auditChain`. **Import CSV Ventes non couvert par ce correctif** (`handleImportCSV`, même fichier) : garde son propre calcul de secours basé sur `DB.ventes.length`, un import restant une action ponctuelle admin synchrone sur toutes ses lignes (pas de risque de collision avec lui-même) ; le risque résiduel — collision avec une vente saisie ailleurs pile pendant l'import — est le même défaut que l'ancien calcul et n'a jamais été observé sur les 9 collisions trouvées (toutes venaient de ventes saisies une par une). À corriger si ça arrive un jour en pratique (transaction par ligne, plus lent pour un gros CSV). `npx tsc --noEmit` : 0 erreur.

Signalé par l'utilisateur via une capture d'écran de `ClientsSection.tsx` → "Modifier le client" → section "Position géographique" : Google Maps affiche son propre bandeau d'erreur générique directement dans le conteneur de la carte, au lieu de la carte. Deux bugs réels trouvés et corrigés au passage (voir historique en commentaire dans `Map.tsx`, section `MapView`/`init()`) :
1. `client/index.html` contenait un `<script src="%VITE_ANALYTICS_ENDPOINT%/umami" data-website-id="%VITE_ANALYTICS_WEBSITE_ID%">` — reliquat Manus (ces deux variables ne sont définies nulle part, ni en local ni sur Vercel) — laissant un `%` non substitué dans une URL de script bien réelle du DOM (`URIError: URI malformed` observé). Google Maps semble trébucher dessus en scannant `document.scripts` à son démarrage. Fix : ce script ne s'injecte plus dynamiquement que si les deux variables sont réellement définies (sinon rien ne s'injecte).
2. `getMapScriptUrl()` avait `loading=async` (ajouté puis retiré dans cette même session) : ce mode différé suppose `google.maps.importLibrary()`, incompatible avec le pattern classique `script.onload` de ce fichier — provoquait par moments `TypeError: window.google.maps.Map is not a constructor` alors que `google.maps.Map` existait bien quelques secondes plus tard. Retiré ; `v=quarterly` (au lieu de `weekly`) et `language=fr` conservés.

Un filet de sécurité "watchdog" (timeout 8s + `tilesloaded`) ajouté puis retiré dans la même session : il déclenchait de faux positifs et son bouton "Réessayer" provoquait un démontage/remontage du conteneur pendant que l'init interne asynchrone de Google Maps (IntersectionObserver sur le conteneur, cartes vectorielles) était encore en cours, causant un second crash (`Failed to execute 'observe' on 'IntersectionObserver'`). Retiré : seul le `try/catch` synchrone autour du constructeur `new google.maps.Map(...)` (avec bouton "Réessayer" pour ce cas précis) reste en place.

**Cause dominante, non corrigeable dans le code : `RefererNotAllowedMapError`.** Une fois ces deux bugs corrigés, l'erreur persistait — reproduite de façon déterministe sur plusieurs clients (`ALPHA ROND POINT YOFF`, `KOTO-IMAM`), sur onglet neuf, avec la requête `maps/api/js` renvoyant bien un 200 : la console affiche `Google Maps JavaScript API error: RefererNotAllowedMapError ... Your site URL to be authorized: http://localhost:3000/`. Confirme et recoupe exactement la note déjà présente plus haut dans ce fichier (§ "Repo hygiene cleanup", point 4, 2026-08-18) : les restrictions HTTP-referrer de la clé (`VITE_GOOGLE_MAPS_API_KEY`, identique à la valeur encore codée en dur en fallback dans `Map.tsx`) dans Google Cloud Console couvrent probablement l'ancien domaine Manus et/ou le domaine Vercel, mais pas `localhost`. Résultat : la carte ne peut pas fonctionner en développement local tant que cette liste n'est pas mise à jour — **action à faire par l'utilisateur dans Google Cloud Console** (Claude n'y a pas accès) : APIs & Services → Identifiants → cliquer sur la clé → "Restrictions relatives aux applications" (HTTP referrers) → ajouter `http://localhost:3000/*` (et `http://localhost/*` si le port change) à la liste, en conservant les entrées existantes (domaine Vercel de prod). Pas de suppression complète des restrictions recommandée (exposerait la clé à un usage depuis n'importe quel site).

`npx tsc --noEmit` : 0 erreur après ces changements. Voir `claude/fix-google-maps-affichage-2026-09-05.md` dans le projet Claude pour le détail complet de l'investigation.

**Rubrique Actionnaires (`ActionnairesSection.tsx`, added 2026-09-06).** Demande explicite de l'utilisateur : un endroit pour suivre l'argent débloqué par les actionnaires (apport de capital vers l'entreprise) et les dividendes qui leur sont versés (distribution de bénéfice vers l'actionnaire) — deux nouveaux types dans `types.ts`, `Actionnaire` (registre : `nom`, `tel?`, `pourcentageParts?` informatif, `notes?`, `actif`) et `MouvementActionnaire` (`date`, `actionnaireId`, `type: "Déblocage" | "Dividende"`, `montant`, `reference?`, `notes?`).

**Décision explicite de l'utilisateur (question posée avant implémentation) : registre SÉPARÉ, sans aucun effet sur le solde de caisse.** Un déblocage n'est PAS ajouté à `computeSoldeCaisseActuel`/`computeSoldeCaisseAuDate` (helpers.ts) comme le sont les Apports, et un dividende n'est PAS traité comme une Dépense/un Versement — ces deux fonctions et les rubriques Apports/Versements/Dépenses restent totalement inchangées. Choix fait pour ne pas toucher un calcul déjà signalé comme fragile à plusieurs reprises dans ce fichier (voir "Balance vs flux" plus haut) ; si un suivi de caisse réel est voulu plus tard, il faudra explicitement étendre `computeSoldeCaisseAuDate` (entrée pour "Déblocage", sortie pour "Dividende") en assumant le risque de régression que ça implique sur ce calcul partagé.

Stocké en `META_FIELDS` (`AppContext.tsx`) — même format léger single-document que `employes`/`commerciaux`/`commandes` (`meta/data`), volume attendu très faible (quelques actionnaires, quelques mouvements par an) ne justifiant pas `ENTITY_COLLECTIONS`. **Réservé aux admins à trois niveaux**, même traitement que `users`/`params` (données d'actionnariat/dividendes jugées aussi sensibles) : (1) `ROLE_SECTIONS` (helpers.ts) n'inclut `"actionnaires"` que dans la liste `admin` — invisible pour caissier/commercial/lecteur ; (2) `ADMIN_ONLY_META_FIELDS` (`AppContext.tsx`, `saveToFirestore`) exclut désormais aussi `actionnaires`/`mouvementsActionnaires` de l'écriture `meta/data` d'un rôle non-admin, comme `users`/`params` ; (3) `firestore.rules` `match /meta/{docId}` : `metaAdminOnlyFieldsUntouched()` et la condition `allow create` traitent ces deux champs comme `users`/`params` — un rôle non-admin ne peut ni les créer ni les modifier, même par un appel direct au SDK/DevTools. **Nécessite `firebase deploy --only firestore:rules` pour être effectif** — même remarque de déploiement que pour tout changement de `firestore.rules` dans ce fichier.
